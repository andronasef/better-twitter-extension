Every value in `01-UI-SPEC.md` was chosen to match X's own rendering rather than to express a separate brand — the extension has no brand of its own inside the popup.

Output: The complete Phase 1 popup, matching the approved UI design contract.

  <behavior>
    - A body background of `rgb(255, 255, 255)` derives scheme `light`.
    - A body background of `rgb(0, 0, 0)` derives scheme `dark`.
    - A body background of `rgb(5, 5, 5)` also derives scheme `dark` — X ships both near-black values.
    - Any other value, including a slate-blue value, derives scheme `unknown` and is still cached verbatim alongside it.
    - `resolveScheme` given `unknown` or `null` returns the browser's `prefers-color-scheme` result, and given a known scheme returns it unchanged.
    - The probe writes `local:xTheme` on first detection and on every subsequent change, and writes nothing when the observed value is unchanged.

  <action>
Create `lib/theme.ts` holding the mapping, shared by the content script and the popup so the two cannot drift. Export `schemeForBackground(value)` mapping an observed background-colour string to `light`, `dark`, or `unknown`, and `resolveScheme(cached)` applying the `prefers-color-scheme` fallback.

Derive the scheme **by value, with an explicit unknown branch** — never by a hardcoded list of X's theme names. X removed its slate-blue Dim theme from the web in February 2026 and now ships two schemes, with a Dim cohort possibly still alive somewhere. A name-based union is what turns "unknown theme" into "popup renders wrong" instead of "popup falls back gracefully"; a value-based map with an unknown branch degrades correctly for any value X invents next. Map `rgb(255, 255, 255)` to light, and both `rgb(0, 0, 0)` and `rgb(5, 5, 5)` to dark. Cache the raw observed string alongside the derived scheme so a future cohort's value can be diagnosed from the stored record without a code change.

Create `entrypoints/x.content/theme-probe.ts` exporting `startThemeProbe`. Read `document.body.style.backgroundColor` — X writes the theme as an **inline style on the body**, so this is the cheap, layout-free read; do not use the computed style. Register a `MutationObserver` on the body with `attributes: true` and `attributeFilter: ['style']` through `lib/observers.ts`'s **global** scope, so it survives route changes. On first detection and on every change, write `xThemeItem` with the raw colour, the derived scheme, and a timestamp; write nothing when the value is unchanged. `document.body` is null at `document_start`, so defer the probe behind the same element-wait the pipeline already uses.

Wire `startThemeProbe` into the content-script bootstrap.

Populate the popup's colour tokens from the UI-SPEC Color tables. `assets/tailwind.css` already declares the token names; fill in both schemes: background `#FFFFFF` light / `#000000` lights-out, surface `#F7F9F9` / `#16181C`, foreground `#0F1419` / `#E7E9EA`, muted `#536471` / `#71767B`, border `#EFF3F4` / `#2F3336`, accent `#1D9BF0` both, destructive `#F4212E` both (declared but unused in Phase 1 so later phases do not invent a second red), warn `#E07C00` / `#FF9500`. The warn token is for the miss icon and the badge dot **only** and is never a text colour — the lighter value on white is roughly 2.9:1 and fails AA.

Solve the first-paint flash in the order the UI-SPEC specifies, because the popup's theme comes from an asynchronous storage read and a naive implementation paints the wrong scheme for one frame. First, `assets/tailwind.css` defines both palettes under `prefers-color-scheme` media queries, which is synchronous and makes first paint already plausibly correct with zero JavaScript. Second, on resolve, the cached X theme overrides the variables on the popup root — for the common case where X's theme agrees with the OS, nothing visibly changes. Third, the shell renders immediately while switches render in position but disabled until settings resolve. No spinner, no skeleton shimmer, no layout shift: a 360x480 surface that flashes a loading state looks broken in a way that a sub-frame disabled switch does not.

Vendor the popup typeface. If Task 1 was approved for the package path, add `@fontsource/inter` as an exactly-pinned dev dependency and copy its static **latin-subset 400 and 700 cuts** into `public/fonts/inter-400.woff2` and `public/fonts/inter-700.woff2`, plus its OFL licence text to `public/fonts/OFL.txt`. Two static Latin cuts land around 25-35KB each; the variable full-range file is 300KB-plus for weights this contract never uses, so do not take it. If Task 1 was answered "vendor", commit the same two files from the official upstream release by hand with the same licence text.

Declare the faces in `entrypoints/popup/popup.css` as family `BTPopupSans` at weights 400 and 700, each `src` resolved through `browser.runtime.getURL`, with `font-display: block`. Blocking is correct here specifically and is the one place this contract departs from swap: the file is local, so the block window is a disk read measured in single-digit milliseconds, and blocking briefly beats a visible reflow from fallback metrics in a 360px popup. Set the popup's stack to `BTPopupSans` followed by X's own fallback chain copied verbatim — the system UI families X names, in X's order — so every degraded case matches X's degraded case.

Three constraints this mechanism must respect. Do not bundle X's Chirp binary: it is commissioned proprietary type and shipping it in a Chrome Web Store package is a licensing exposure with no upside. Do not fetch a font at runtime from any origin, including X's own asset CDN — zero outbound requests is a deliberate user-chosen invariant. Do not add an extension-pages content-security-policy override to the manifest: Chrome's default MV3 extension-page policy constrains script and object sources only, an extension-origin font needs no manifest change, and an override is a store-review flag for zero benefit. If one appears necessary, the diagnosis is wrong.

Declare the two font files in `web_accessible_resources` only if the shadow-root surfaces of a later phase need them; the popup is an extension-origin document and reaches `public/` without a WAR entry. Do not widen the existing scoped entry.

Write `tests/unit/theme.test.ts` covering every bullet in the `<behavior>` block, including the unknown branch and the unchanged-value no-write case. Write the tests before the implementation and confirm they fail first.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| x.com DOM → theme probe | X's inline body style is untrusted input read across the page boundary |
| `chrome.storage.local` → popup render | Cached theme and diagnostics records drive what the popup paints |
| popup document → any origin | The boundary the zero-outbound-request invariant closes |
| redistributed font binary → Chrome Web Store package | A licensing boundary, not a technical one, but a real review-blocking one |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Tampering | a DOM-derived colour string reaching a style sink | medium | mitigate | The observed background string is only ever compared against a fixed value map and stored; it is never assigned into a style property or interpolated into CSS. The derived scheme, not the raw value, selects the palette |
| T-04-02 | Information Disclosure | an outbound font or asset request from the popup | high | mitigate | Every `@font-face` source resolves through the extension origin, asserted by a check that no stylesheet references an external origin. Encoded as a prohibition on this plan, because it is what makes the published privacy claim unqualified |
| T-04-03 | Tampering | a diagnostics record rendered as HTML in the warning strip | medium | mitigate | The warning strip renders fixed UI-SPEC copy plus the feature's registered title; it never renders a stored selector string or any page-derived value, and all rendering goes through React rather than an HTML-parsing sink |
| T-04-04 | Elevation of Privilege | an extension-pages content-security-policy override added to satisfy the bundled font | high | mitigate | No override is added. Chrome's default MV3 extension-page policy constrains script and object sources only, so an extension-origin font needs no manifest change; the built manifest is asserted to carry no override |
| T-04-05 | Repudiation | shipping a proprietary typeface in a store package | high | mitigate | The bundled face is openly licensed and its licence text ships alongside it in the package. | T-04-07 | Denial of Service | the theme observer firing on every body style mutation | low | accept | The observer is filtered to the `style` attribute and exits on an unchanged value before any write.
