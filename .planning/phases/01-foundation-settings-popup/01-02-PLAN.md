<objective>
Give the extension eyes: a MAIN-world bridge that observes X's own network traffic and navigations, a layered route watcher that keeps every feature alive across client-side navigation, and a named observer registry that tears page-scoped work down so a long session does not leak.

Purpose: x.com is a client-routed SPA whose content scripts do not re-run on navigation and whose timeline node is replaced, not reused, when a tab is revisited. Without this plan the tracer from 01-01 works on a hard reload and dies on the first in-app click. The bridge also runs spike S2, whose captured GraphQL shapes are the direct input Phases 3 and 4 build against — running it now is what de-risks both.

Output: A working route watcher, an observation bridge that never touches the page's behaviour, and two committed spike notes.
</objective>

<assumption_delta_decision>
The assumption-delta detector fired on this phase with a `pluralization` signal (term: `fallback`, from the ROADMAP spike text "Navigation API primary with a history patch fallback"). The core assumption that lost its monopoly is **"there is one way to know x.com navigated."** There are four, and Plan 01-03 will show the same shape again for selectors: there is no longer one selector string, there is an ordered chain.

- **Primary noun:** `NavigationSignal` — a source-tagged `{ url, source }` record — not "the history patch". A signal has a source; the watcher is defined over a set of sources.
- **Decision:** `promote`, not `add-alongside`. The general representation (a set of registered navigation sources funnelled into one debounced `onRouteChange(url)`) is the primary; each specific mechanism — bridge event, `popstate`, `<title>` observer, `wxt:locationchange` — is demoted to one variant registered into it. Rationale: adding a fallback alongside a still-privileged primary means a future source that does not fit the primary's assumptions (a bridge failure, a cohort where `<title>` is set asynchronously) can be registered but never confirmed as authoritative. Promoting makes "which source fired" a data field rather than a branch, which is also exactly what spike S1 needs in order to report an answer without a code change.
- **Accepted consequence:** none. No debt is taken on; this is the cheaper shape.
- **Invariant test (accepted, built in Task 2):** every registered navigation source funnels through the single debounced `onRouteChange`, and the same URL arriving from two sources inside the debounce window produces exactly one handler run. That test goes red the instant a future phase wires a source directly to a handler and reintroduces the singular assumption.
</assumption_delta_decision>

  <action>
Create `entrypoints/bridge.ts` as a WXT `defineUnlistedScript`. It runs in the MAIN world, in x.com's own JavaScript context, and it has no access to `chrome.*` whatsoever — importing anything from `lib/` that touches `browser.*` produces a silent runtime `undefined`, so this file imports nothing from the rest of the codebase. Keep it to three patches plus an event emitter.

Capture `document.currentScript` at the top of the script body and emit every event by dispatching a `CustomEvent` on that node. Do **not** use the window-level cross-context messaging API: events dispatched there are broadcast to every listener on `window`, including every other extension and every page script, which is an information-disclosure path the `CustomEvent`-on-the-script-node channel closes for free. The reference implementation this research drew from removes its script node and falls back to the window-level channel — do not copy that.

Patch `window.fetch`: await the native call, return its result unchanged, and only then inspect the URL. When the URL contains `/i/api/graphql/`, clone the response and parse it off the hot path, swallowing any parse rejection. Wrap the entire observation block so that observation can never break the page.

Patch `XMLHttpRequest.prototype.open` and `XMLHttpRequest.prototype.send`. This half is not optional: X sends GraphQL over XHR as well as fetch, so a fetch-only bridge captures nothing for operations like `TweetDetail` and `HomeLatestTimeline`. Store the request URL on the XHR **instance** under an extension-private property, never in module scope — module scope would mis-bind overlapping in-flight requests to each other, which is the concurrency failure this plan's `must_haves` names explicitly. In `send`, when the stored URL contains `/i/api/graphql/`, attach a one-shot `load` listener that parses `responseText` inside a guard. Always return the native result.

Patch `history.pushState` and `history.replaceState` in the same file and add a `popstate` listener, each announcing the current `location.href` on a `bt:navigate` event. One injected script, three jobs, zero extra cost — and this is the only place in the codebase where the history patch can actually fire.

Emit exactly two event types: `bt:graphql` carrying a shape-only payload, and `bt:navigate` carrying `{ url }`. The `bt:graphql` payload is `{ method, urlPath, operationName, docId, topLevelResponseKeys, entryCount }` — derive `operationName` and `docId` by splitting the path segment after `/i/api/graphql/`, and derive `topLevelResponseKeys` with `Object.keys` on the parsed body's `data` object. **Never** include the response body, the request body, the `variables` value, any header, any cookie, or any tweet content in the payload. The bridge accepts no inbound commands from the page and holds no secrets: every decision and every storage write happens in the isolated world.

Create `entrypoints/x.content/bridge-client.ts` as the isolated-world half. Call `injectScript('/bridge.js', { keepInDom: true, modifyScript })`. `keepInDom: true` is load-bearing — the `<script>` element *is* the channel, so a script that removes itself (or an `onload` handler that removes it) destroys the channel while leaving the patches in place, which presents as "the patch ran, the isolated world sees nothing". Attach both listeners inside `modifyScript`, **before** the script loads, or the first events are lost. Export `startBridge`, `onGraphqlShape`, and `onBridgeNavigate`.

Add the `web_accessible_resources` entry to `wxt.config.ts`: resource `bridge.js`, `matches: ["*://x.com/*", "*://twitter.com/*"]`. Scoped, never `<all_urls>` — an over-broad entry lets any site load the bridge script and fingerprint the install.

Wire `startBridge` into the `entrypoints/x.content/index.ts` bootstrap, before the pipeline starts.

  <behavior>
    - Registering a page-scoped observer under a name already in the page registry disconnects the previous observer before registering the new one.
    - `teardownPageScope()` disconnects every observer in the page registry and empties it, and leaves every observer in the global registry connected.
    - The same URL delivered from two different sources inside the debounce window results in exactly one `onRouteChange` handler invocation.
    - A URL identical to the last-seen URL results in zero handler invocations, regardless of source.
    - A URL differing from the last-seen URL results in exactly one handler invocation, and `teardownPageScope` runs before page setup re-runs.
  </behavior>
  <action>
Create `lib/observers.ts` with two named registries: `globalObservers` for observers that must survive navigation (the `<body>` style observer, the `<title>` observer) and `pageObservers` for observers torn down on every route change (the timeline observer, tab containers). Export `observeElement(name, target, callback, options, scope)` which, before registering, disconnects any observer already registered under that name in that scope — this is the mechanism that keeps a long session from accumulating observers across dozens of navigations. Export `registerGlobalObserver`, `registerPageObserver`, and `teardownPageScope`.

Combine this with WXT's own lifecycle helpers, which are the other half of FOUND-09: use `ctx.addEventListener`, `ctx.setTimeout`, `ctx.setInterval`, and `ctx.requestAnimationFrame` rather than the raw globals, because they stop firing when the extension context is invalidated by an update or reload, and check `ctx.isValid` before work that outlives a tick. For raw `addEventListener` on page nodes, pass a `signal` from an `AbortController` scoped to the page and abort it in `teardownPageScope`.

Create `entrypoints/x.content/route-watcher.ts` implementing the promoted shape recorded in the `<assumption_delta_decision>` block: a set of registered navigation sources, each producing a source-tagged `{ url, source }` signal, all funnelled into one debounced `onRouteChange(url)` that no-ops when the URL equals the last-seen URL. The cost of the redundancy is one string compare. Register four sources, in this priority order:
  1. `bridge` — `onBridgeNavigate` from Task 1. Primary. This is the only source that sees a page-initiated `pushState`.
  2. `popstate` — a `popstate` listener in the isolated world. DOM events are shared across worlds so this does fire, but it covers back and forward only; `pushState` does not fire it.
  3. `title` — a `MutationObserver` on the document title, registered in the **global** scope so it survives route changes. Handle the documented "Flash of Uninitialised Title" case: X sets the title asynchronously and briefly renders the bare product name, so a title equal to the bare product name must not be treated as a navigation. This is the bridge-failure net.
  4. `locationchange` — WXT's built-in `wxt:locationchange` event. It works but it is a one-second poll, so it is the last-resort net and never the primary; a visible lag between navigating and features reapplying is exactly what it would cause if promoted.

Expose which source won each route change on the signal record, so spike S1 can report an answer without a code change and so a dev-mode log makes a dead bridge channel obvious on the first manual click.

Rewire `entrypoints/x.content/index.ts` so that `onRouteChange` first calls `teardownPageScope()` and then re-runs page setup: re-resolve the timeline, restart the pipeline, and re-dispatch enabled features. Handle the two documented x.com behaviours here, both of which are silent-failure sources: a timeline element with no `style` attribute is a placeholder and must not be observed — wait for the styled element; and when a tab that has been viewed before is revisited, X **replaces** the timeline node rather than reusing it, so the pipeline must observe the timeline's parent for replacement instead of assuming a stable timeline node for the life of the page. An observer left attached across a route change keeps a detached node alive and leaves the new timeline unobserved.

Write `tests/unit/observers.test.ts` and `tests/unit/route-watcher.test.ts` covering every bullet in the `<behavior>` block above, including the invariant test named in the assumption-delta decision. Write the tests before the implementation and confirm they fail first.

Add `e2e/route-change.spec.ts`. Extend `e2e/fixtures/x-home.html` with a second view and a control that calls `history.pushState` to switch between them, replacing the timeline node on the way (mirroring the tab-revisit behaviour). The spec asserts that after a simulated client-side navigation the promoted cell in the new view is hidden, proving the watcher plus teardown plus re-setup chain works on a replaced timeline node without a reload.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| x.com MAIN world → injected bridge script | The bridge runs inside x.com's own JS context and is fully visible and tamperable by page code |
| injected bridge `<script>` node → isolated-world content script | The `CustomEvent` channel carrying observed shapes across the world boundary |
| X's authenticated network traffic → bridge observation point | The bridge sits inside a logged-in session and can see request URLs, headers, and response bodies |
| extension package → any web origin | `web_accessible_resources` determines who can load `bridge.js` |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Tampering | page JS tampering with the MAIN-world bridge | medium | mitigate | The bridge is observation-only: it accepts no inbound commands, holds no secrets, makes no decisions, and performs no storage writes. Every decision and every write happens in the isolated world, so the worst a tampered bridge achieves is suppressing or forging a shape event, which degrades a dev-only log |
| T-02-02 | Information Disclosure | `CustomEvent` payload reaching other extensions or page scripts | medium | mitigate | Events are dispatched on the injected `<script>` node, never on the window-level broadcast channel. Asserted by an automated check against `entrypoints/bridge.ts` |
| T-02-03 | Information Disclosure | X session material visible on intercepted requests (cookies, `x-csrf-token`, bearer tokens) | high | mitigate | The emitted payload is a closed set of six shape-only keys — method, urlPath, operationName, docId, topLevelResponseKeys, entryCount — asserted by acceptance criteria. No header is read, no cookie is read, and nothing is persisted |
| T-02-04 | Information Disclosure | over-broad `web_accessible_resources` enabling extension fingerprinting | high | mitigate | The single WAR entry is scoped to `matches: ["*://x.com/*","*://twitter.com/*"]`, asserted against the built manifest. Any site could otherwise load `bridge.js` and detect the install |
| T-02-05 | Tampering | observed GraphQL JSON treated as trusted input | medium | mitigate | Captured JSON is validated for shape before any key is read and fails closed on mismatch. No captured value is interpolated into a selector string or assigned through an HTML-parsing sink |
| T-02-06 | Repudiation | a spike note recording an assumption as an observation | medium | mitigate | Both notes ship with a `PENDING LIVE RUN` marker that a human replaces with real values; the marker's presence is asserted by the automated verify, so an unrun spike is visible rather than silently plausible |
| T-02-07 | Denial of Service | an observation failure propagating into x.com's own request path | medium | mitigate | Every observation block is wrapped and every patched function returns the native result unchanged and synchronously; parse failures are swallowed. Encoded as a prohibition on this plan |
